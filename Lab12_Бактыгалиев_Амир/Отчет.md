## 🧠 4. Ответы на контрольные вопросы


#### Вопрос 1: Чем аутентификация отличается от авторизации?
**Ответ:**  
Аутентификация (Authentication) — это процесс проверки подлинности личности пользователя (ответ на вопрос «Кто ты?» через проверку логина/пароля или токена). Авторизация (Authorization) — это проверка прав доступа уже опознанного пользователя к конкретному ресурсу или действию (ответ на вопрос «Что тебе разрешено делать?»).



#### Вопрос 2: Что такое JWT и из каких частей он состоит?
**Ответ:**  
JSON Web Token (JWT) — компактный текстовый формат безопасной передачи клеймов (утверждений) между сторонами. Состоит из трех частей, разделенных точками: 1) Header (алгоритм хеширования и тип токена); 2) Payload (полезная нагрузка с данными пользователя, ролями и сроком действия exp); 3) Signature (цифровая подпись, вычисленная по секретному ключу сервера для защиты от подделки).



#### Вопрос 3: Шифрует ли JWT содержимое payload?
**Ответ:**  
Нет! Стандартный JWT подписывается (JWS — JSON Web Signature), а не шифруется. Payload кодируется лишь алгоритмом Base64URL, и любой клиент или посредник может свободно декодировать и прочитать его содержимое. Поэтому в payload категорически запрещено помещать пароли, номера карт или приватные секреты.



#### Вопрос 4: Что такое серверная сессия?
**Ответ:**  
Серверная сессия — это механизм сохранения состояния на стороне сервера. При успешном входе сервер генерирует уникальный случайный Session ID, сохраняет данные пользователя в своей базе/Redis, а клиенту передает только cookie с Session ID. При каждом последующем запросе сервер находит сессию по ID в хранилище.



#### Вопрос 5: Зачем нужны флаги HttpOnly, Secure и SameSite для cookie?
**Ответ:**  
HttpOnly запрещает доступ к cookie из клиентского JavaScript (через document.cookie), защищая сессию от кражи при XSS-атаках. Secure гарантирует отправку cookie исключительно по зашифрованному протоколу HTTPS. SameSite (Strict/Lax) предотвращает автоматическую отправку cookie в межсайтовых запросах, защищая от CSRF-атак.



#### Вопрос 6: Почему localStorage не рекомендуется для хранения чувствительных токенов?
**Ответ:**  
Хранилище localStorage полностью доступно любому скрипту, выполняющемуся на странице. В случае внедрения даже малейшей XSS-уязвимости злоумышленник может мгновенно прочитать access/refresh токены и скомпрометировать учетную запись пользователя.



#### Вопрос 7: Чем OAuth 2.0 отличается от OpenID Connect (OIDC)?
**Ответ:**  
OAuth 2.0 — это протокол делегированной авторизации (предоставление права приложению действовать от лица пользователя, например читать фото через Access Token). OpenID Connect — это надстройка идентификации над OAuth 2.0, добавляющая ID Token (JWT) для подтверждения аутентичности пользователя.



#### Вопрос 8: Что такое access token и refresh token?
**Ответ:**  
Access token — короткоживущий токен (срок жизни 5–15 минут), передаваемый в заголовке Authorization: Bearer для доступа к защищенным API. Refresh token — долгоживущий токен (дни/недели), безопасно хранящийся в HttpOnly cookie, используемый сервером для выдачи нового access token без повторного ввода логина и пароля.



#### Вопрос 9: Зачем проверять срок действия (exp) JWT?
**Ответ:**  
Проверка клейма exp (expiration time) предотвращает бессрочное использование украденного токена. Если срок действия истек, сервер отклоняет запрос со статусом HTTP 401 Unauthorized, заставляя клиента обновить токен или войти заново.



#### Вопрос 10: В чем различие между HTTP 401 Unauthorized и 403 Forbidden?
**Ответ:**  
HTTP 401 Unauthorized означает, что запрос не аутентифицирован: токен отсутствует, просрочен или невалиден (требуется вход). HTTP 403 Forbidden означает, что личность пользователя подтверждена, но у него недостаточно прав (роли) для доступа к запрашиваемому ресурсу.



#### Вопрос 11: Почему нельзя полагаться только на скрытие кнопки в интерфейсе?
**Ответ:**  
Клиентский код полностью контролируется пользователем и может быть легко модифицирован через DevTools или прямой вызов fetch(). Скрытие кнопки — это лишь элемент UX. Настоящая безопасность должна обеспечиваться валидацией токена и прав строго на стороне сервера.



#### Вопрос 12: Что должно происходить при выходе пользователя (logout)?
**Ответ:**  
При выходе сервер должен уничтожить серверную сессию или внести токен в черный список (blacklist/revoke), очистить cookie сессии на клиенте (Set-Cookie с истекшей датой), а клиент должен удалить кэшированные данные из памяти и перенаправить пользователя на форму входа.
